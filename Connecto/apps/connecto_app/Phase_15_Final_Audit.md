# Phase 15 Final Audit: Domain Service Isolation

## Architecture Changes
- Introduced a unified `MessageBus` interface and `AppMessageBus` implementation in `lib/core/messaging/`.
- Centralized message route definitions (`networkOnly`, `nativeOnly`, `broadcast`) allowing services to precisely target where outbound payloads are dispatched.
- Replaced `DeviceTransport` and `NativePlatformBridge` inside `ClipboardSyncManager`, `ShareManager`, `FileTransferManager`, and `NotificationManager` with `MessageBus`.
- Wrapped raw JSON payloads in a new `BusMessage` model which standardizes identity extraction and typing across feature consumers.

## Message Flow
1. Network and IPC events are captured by `AppMessageBus` from `DeviceTransport` (WebSocket) and `NativePlatformBridge` (MethodChannel).
2. Incoming raw JSON maps are parsed into `BusMessage` instances.
3. The `AppMessageBus` intercepts incoming payloads and subjects them to the deduplication mechanism.
4. Downstream services observe streams generated by `messagesOfType(String prefix)`, automatically scoping domain services to their domains.
5. Outbound requests are sent directly via `MessageBus.send()` where routing strategy (`networkOnly`, `broadcast`, `nativeOnly`) determines final delivery paths. 

## Routing Implementation
The `MessageRoute` enum explicitly drives the outgoing flow within `AppMessageBus`:
- `MessageRoute.networkOnly`: Sends message securely over the device-to-device transport (`DeviceTransport`).
- `MessageRoute.nativeOnly`: Translates message to IPC payload directed to the Android OS level (`NativePlatformBridge`).
- `MessageRoute.broadcast`: Distributes message down both pipelines concurrently.

## Deduplication Mechanism & Transport Failures
- **Runtime Duplicate Suppression**: 
  - `AppMessageBus` caches a unique payload footprint. It first searches for explicit keys (`id`, `transferId`). If omitted, it generates a full payload `SHA-256` digest string.
  - State is constrained structurally to an LRU cap (100 messages max) and temporally by a 5-second TTL.
- **Transport Delivery Guarantee**:
  - Outgoing dispatches are executed "best effort". Disconnected transports, IPC disruptions, or serialization exceptions are caught and suppressed to guarantee domain stability. Feature services function optimally ignorant of actual transport integrity.

## Feature Isolation Verification
The following services were successfully refactored and proven completely agnostic to underlying transport technologies:
- `ClipboardSyncManager`
- `ShareManager`
- `FileTransferManager`
- `NotificationManager`

*Proof*: Code statically imports `core/messaging` dependencies without referencing any specific transport platform channel or cross-device APIs.

## Remaining Technical Debt
- Some legacy types inside the old `message_types.dart` still remain. A future refactor could combine them exclusively into `message_types.dart` under the `core/messaging` umbrella.
- The UI layer still relies directly on `DeviceTransport` for specific tasks (like triggering battery status requests). Depending on architectural purity goals, this could be isolated further behind a generic `DeviceStatusManager` in a future phase.
